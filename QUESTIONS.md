1397. **What the keyboard cannot reach, and where it is left standing.** (Raised 2026-09-16, same pass.)

925. **Three more things git knows about overlapping patches, parked** (raised 2026-08-27 with 924; **Ed: park for now** — each wants design work on how it is communicated before it is worth a mechanism). **(a) Dependent candidates.** `propose-edit` (K24) starts a draft from a candidate's wording, so C can be built on unadopted A; if A loses, C's rebase onto the incumbent fails over a decision made elsewhere. *Presupposes* is a different relation from *composes* (§2.2's lattice), and git's stacked patches say: declare it at submission, adopt in order, and let C fall with A or return to its author with A's fate stated. Verify what the engine does today first. **(b) A candidate's version chain.** §2.4's blanket *evidence resets* does not distinguish a clean rebase (no words changed) from an author's revision; Mercurial's obsolescence markers give a change an identity across rewrites, each recording what it superseded and why, so the rule can be *rebase keeps, revision resets*. With it, git's `rerere`: an author's confirmation against new text is remembered and reused when the same span moves again, instead of the leader failing identically every batch. **(c) Two cheap ones**, no spec change: a base-independent content hash of the normalised hunk (`patch-id`) before the dedup gate asks the LLM, and an interdiff — what moved under you, not the whole new paragraph — on the confirm-against-new-text card.

### Queue ordering — what survives Ed's 104–108

Ed replaced ranked ordering with a **margin index** (2026-08-16): entries stand beside their own clauses in document order, sealed items are dots, a patch appears once per site. Urgency was carried by colour strength and card size; since 2026-08-16 the card sizes are equal and urgency instead decides **which** entries fit on the screen, so the number now gates visibility rather than compression — which makes 98 below considerably more load-bearing than it was. That closed 99 (document position doesn't move when others judge), 101 (sealed stay, as dots — the rail is a map, and a map shows settled ground) and 103 (there are no serving *slots* left to explain; everything is shown at once). Three remain, all about the urgency number itself rather than about order.
109. **Scale: the margin assumes a short rail.** Sixteen entries beside a twenty-page charter is a map you can scan. 282. **A rendered document and a source offset do not agree** — **Q1467 removes its subject** (Ed, 2026-09-19, built): edit mode shows the markdown source, so a caret offset in a block *is* an offset into that block's line and the composer has nothing left to map; `richToSource` is deleted and `sourceToRich` survives only where the founder's pre-🍾 column crosses between its read view and its edit view. It stays here for whatever is still owed at that one seam, if anything is. (Raised 2026-08-17, from 279's build; Ed asked for a recommendation the same day.) The charter fixture is plain text, so the composer can take a caret offset straight from the DOM and use it against the clause's source. The moment the *document* renders markdown that stops being true: a DOM selection measures the rendered text, and `**bold**` is four characters there and eight in the source, so every offset the composer computes is wrong by two for each mark above the caret.

**Recommendation: render markdown in the document, and make the rendered→source mapping a property of the block rather than of the composer.** One function that takes a block element and a DOM position and returns a *source* offset, used by everything that asks the question — `offsetIn`, `startDraftFromTyping`, `startDraftFromRun`. The arithmetic already exists (`richToSource` / `sourceToRich`, written for the lane's view toggle); what matters is that exactly one place knows about the distinction, because the failure mode here is a two-character drift that nothing complains about and no test catches unless the test happens to put a mark above the caret.

Two other options, for the record. Keep the charter plain and let markdown live only inside candidates — cheapest, but an adopted candidate would then print its asterisks into the charter, so it only defers the problem to the first adoption. Or store the document rendered and treat markdown purely as import/export — which gives up "the characters you see are what is stored", and that was the whole reason 279 chose source-of-truth markdown in the first place.

**Do it before the charter carries any formatting**, not after. Until then every test passes and the bug does not exist; the day somebody bolds a word near the top of a long clause it exists everywhere at once, and it will look like a caret bug rather than an offset bug.

**Deferred past the alpha, deliberately** (Ed, 2026-08-27, answering this from the alpha-readiness plan's Track 3.3 — plan-queue **77**, backlog entry 77; the plan had said *fix before the day*). Option **(b)**: the charter stays plain text for the alpha and the rendering is done afterwards. Nothing changes before the day.

Three facts the deferral rests on, checked in the tree at `0d160ad` rather than assumed. **The charter renders plain text today** — `design/session.js:2994` and `:3009` emit `esc(line.x)`, so a clause carrying `**bold**` prints its asterisks — which means the bug is not merely unobserved but *unreachable*: `offsetIn` (`design/session.js:1875`) measures rendered text, and for a plain-text document that **is** the source. **The recommendation above is not a bug fix**, it is *render markdown in the document*, a visible change to what every reader of every charter sees; the arithmetic it needs already exists as `richToSource` / `sourceToRich` (`design/cards.js:342`, `:352`), but the change also moves `design/tools/card-copy.golden.json`, both frozen probes, `scripts/journey-walk.mjs`'s caret and propose steps, and what `design/STYLE.md` takes a clause to be. What the deferral costs, stated so nobody rediscovers it as a surprise: **if an alpha room does adopt a clause carrying a mark, that document's offsets are quietly wrong from then on** — in a throwaway document, which is the whole of why this is affordable. The two other options are on the record above and neither is rejected; (c), building only the block-to-source mapper without changing what renders, remains the cheap half of (a) if the rendering is wanted in a hurry.

What it needs a ruling on is the evidence. A revision is a **new candidate**: any comparisons already cast against the old wording were cast against a text that no longer exists, so they are discarded exactly as a ground shift discards yours (§4.4). That is correct and it is also a real cost — revise a proposal that six people have already judged and you have thrown their work away, and they will be served the pair again. Three ways. (a) **Always allowed, evidence always resets** — simple, honest, and quietly expensive on a busy race. (b) **A grace window**: free revision until the first judgment lands on it, and after that it is withdraw-and-repropose with the cost visible. This matches what the request is actually about — *immediately*, because they saw a mistake — and it makes the common case free and the expensive case explicit. 346. **Sybil resistance at the front door** (Ed, 2026-08-18, parked: *if people can become members via a link, we have to be wary of sybil attacks — perhaps even accidental*). *Note, 2026-08-26 (entry 94): the open door is now 🤝 *yes* with 🪪 at ✒️ — an application admitted on submit — which is exactly where this bites; the same price at 🏛️ or ✏️ puts a room between the link and the membership.* Membership begins at first arrival (§9.6a) and the magic link **is** the credential, so the attack surface is the invitation itself. 315. **The ranking model as a document-creation setting: approval · Bradley–Terry · Crowd-BT** (Ed, 2026-08-17, parked as a note for later). *There are situations where each is appropriate and I think much of our machinery still applies for each.* Crowd-BT is Chen, Bennett, Collins-Thompson & Horvitz, *Pairwise Ranking Aggregation in a Crowdsourced Setting*, WSDM 2013 (10.1145/2433396.2433420) — Bradley–Terry with a **per-judge reliability parameter** estimated jointly with the item scores, plus an active-learning scheme that chooses which pair to serve *and whom to serve it to*. Details want checking against the paper before anything is built on them.

Ed is right that most of the machinery is indifferent to the choice. The `patch-engine`, `overlap-gates` and `dedup-gate` are text machinery and never touch the model. The `adoption-threshold` and its ramp are stated as P(challenger beats incumbent), and all three produce something that plays that role. Quorum, adoption floors, the record, the gazette, and the whole of `session-view` are unaffected — a card asks for a judgment either way.

What genuinely changes is worth listing, because it is more than the estimator. **Active sampling largely disappears under approval**: everybody can rate everything, so the `router` stops *selecting* and only *orders*, which would make the queue dramatically shorter and the `evidence-meter` mean something different. **Deadlock (§8.3) is a Bradley–Terry construct** — *close relative to the marginal value of further sampling* — and under approval it becomes two candidates with similar approval rates, which is detectable but is not the same claim. **Indifference** has no separate existence under approval; approving both *is* indifference. And the **`bounty score`** rests on resolvable disagreement, which is model-specific.

Two things worth having written down before this is picked up.

**The choice is constitutional, not statistical.** Crowd-BT's reliability parameter says a judge is *often wrong*, which presupposes there is a right answer to be wrong about. This project's §3.3 says the opposite in as many words — *preference is not measurement*. If Hollis prefers the shorter clause and thirteen people prefer the longer one, Hollis is not unreliable; Hollis disagrees. Down-weighting a judge is **disenfranchising them by an algorithm nobody in the room can audit**, which is a serious thing to do to a member of a constitutional convention. But there are documents where it is exactly right — a technical standard, a specification being cleaned up, any domain where some readings are simply mistakes — and those are the same documents where a large roster contains people of very different expertise. So the real question a convenor is answering is **does this document treat disagreement as difference or as error**, which is the kind of question that belongs at `document-creation` or the `founding-ceremony` beside quorum and the bar, and not in a settings menu. Under the §9.0a logic it is arguably the roster's to settle rather than the convenor's: being told your judgments count for less is a thing done *to* you.

**And the sophisticated model is probably wrong at v1 scale.** Crowd-BT spends data on extra per-judge parameters, and CLAUDE.md tunes v1 for rosters of 5–10 where data-efficiency beats throughput; on fourteen judges it may be strictly worse than plain Bradley–Terry, which is itself chosen over approval *because* it extracts more per judgment. Crowd-BT's home is hundreds of annotators. Which puts its threshold at roughly the roster size where you stop being able to know everyone — the same point at which a room stops being able to vouch for each other's good faith. Those two thresholds coinciding is not a coincidence, and it is the strongest argument that this is a real setting rather than a knob: **the model should change when the room changes kind.**

One reversal to expect if approval is built: it produces the **more legible record**. The `sealed record`'s best sentence — *these two beat what we had and those three did not* — is currently a Bradley–Terry construction in which every number is a probability against the incumbent. Approval counts are less informative and far easier for a lay reader to trust. The more sophisticated model makes the harder-to-explain record, which matters for a document whose legitimacy rests on people believing the record.
